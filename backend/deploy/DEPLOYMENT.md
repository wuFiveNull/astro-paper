# Production deployment runbook

This runbook is for the AstroPaper Spring Boot + MySQL + Astro SSR stack. It is deliberately separate from the existing `blog` Compose project on the server. The production Compose file uses its own project name, network, and MySQL volume; it does not publish MySQL and keeps the API on a loopback port. For the current private IP-only deployment, the web service is explicitly bound to HTTP port 80.

## Release inputs

The server needs these files in one private directory:

- `compose.production.yaml`
- `.env` copied from `.env.production.example` and filled with private values
- `astro-paper-api.jar` built with `mvn -f backend/pom.xml clean verify`
- a prebuilt Astro SSR image referenced by `WEB_IMAGE`

Build the web image in CI or another trusted build host. Do not run an Astro image build on the current low-memory server while the existing production database is running.

## First deployment to an empty AstroPaper volume

1. Confirm the current `blog-app-1` and `blog-db-1` containers are healthy. Do not stop them as part of this preparation.
2. Copy the release inputs to a new server directory and create the private `.env`.
3. Set `ADMIN_BOOTSTRAP_ENABLED=true` and one-time administrator values only for the first start. Use a password of 12–72 UTF-8 bytes. Remove those values after the first successful login.
4. Start the isolated stack:

   ```bash
   docker compose --env-file .env -p astro-paper -f compose.production.yaml up -d
   ```

5. Check the loopback endpoints before routing public traffic:

   ```bash
   curl -fsS http://127.0.0.1:${API_HOST_PORT:-18083}/api/v1/health
   curl -fsS http://127.0.0.1:${API_HOST_PORT:-18083}/actuator/health
   curl -fsS http://127.0.0.1:${WEB_HOST_PORT:-18084}/
   ```

6. Disable bootstrap variables, recreate only the API service, and log in through the private test path. Verify the API and web logs contain no startup errors.

## Backup before migration or cutover

Run the checked-in script while the MySQL service is healthy:

```bash
BACKUP_RETENTION_DAYS=14 ./backup-mysql.sh
```

The script creates a single-transaction compressed dump and a SHA-256 sidecar under `backups/`. Keep at least one backup outside the server before importing content or changing the reverse proxy. A restore drill should be performed against a disposable MySQL volume before the first public cutover.

The restore helper requires an explicit confirmation variable and a `.sql.gz` file:

```bash
CONFIRM_RESTORE=YES ./restore-mysql.sh /absolute/path/to/backup.sql.gz
```

Use it only against a disposable volume for a drill, or after stopping the cutover and selecting the documented rollback point. It refuses missing confirmation, invalid extensions, and missing files.

## Content migration

On the local workstation, review `backend/target/content-import.sql` generated by `node backend/tools/prepare-content-import.mjs --write --author-id <production-author-id>`. Back up the production database first, then apply the SQL exactly once inside the AstroPaper database. The importer is insert-only and preserves the Markdown source files as the rollback source; it does not modify the existing `blog` database.

## Current IP-only deployment

The current server deployment uses `http://47.118.88.19/` directly. Set these values in the private server `.env` only when this mode is intentionally accepted:

```dotenv
WEB_BIND_ADDRESS=0.0.0.0
WEB_HOST_PORT=80
SESSION_COOKIE_SECURE=false
```

`SESSION_COOKIE_SECURE=false` is required because the site is accessed over plain HTTP. If a domain and HTTPS proxy are added later, bind the web container to a loopback port, set `SESSION_COOKIE_SECURE=true`, and route HTTPS traffic through the proxy.

The checked-in `import-content.sh` helper imports the generated Markdown SQL using the private Compose environment without exposing the MySQL root password in the shell command:

```bash
./import-content.sh /absolute/path/to/content-import.sql
```

Uploaded images are stored in the named `astro_paper_uploads_data` volume and are served through `/api/v1/uploads/images/<generated-filename>`. Before the first API start, make the volume writable by the API uid:

```bash
docker volume create astro_paper_uploads_data
docker run --rm -u 0 -v astro_paper_uploads_data:/data eclipse-temurin:21-jre chown 10001:10001 /data
```

The Astro SSR service proxies browser `/api/v1/*` requests to the internal Spring Boot service. This keeps login, CSRF, article management, and image upload on the same IP and cookie origin while leaving the API port private.

## Reverse-proxy cutover

When HTTPS is introduced, route the selected hostname to `127.0.0.1:${WEB_HOST_PORT}` and `/api/` to the same Astro SSR service (the SSR service proxies browser API requests internally). Keep the old Compose project and its database volume intact until public smoke checks pass and rollback is no longer needed.

Required final checks are HTTPS, session cookie `Secure`, health checks, public article rendering, login/logout, article publish, comment moderation, guestbook processing, RSS, sitemap, and a backup restore drill.
